1. 方案概述

本项目是一个安卓游戏内存修改器（基于 ImGui 悬浮菜单），目标游戏为 和平精英（包名 com.tencent.tmgp.pubgmhd，采用 UE4 引擎）。

在旧方案中，修改器作为独立 App 运行，通过 WindowManager 悬浮窗覆盖在游戏上方，利用 process_vm_readv 跨进程读取游戏内存。这种方式存在根本性限制：跨进程读写其他应用内存需要 root 权限，或依赖 sharedUserId 使两个 App 共享同一 Linux UID —— 而后者要求两方 APK 签名一致，在实际游戏场景中几乎不可行。

新方案「直装（Direct Install）」彻底改变了运行模式：将修改器的核心动态库 libCube.so 直接注入到游戏 APK 内部，使其在游戏进程内运行，无需 root、无需 sharedUserId、无需独立悬浮窗 App。

核心洞察：process_vm_readv 在对自身进程 PID（即 getpid() 返回值）调用时，不需要 root 权限。由于 libCube.so 被注入后运行在游戏进程内，getPID() 直接返回 getpid()，内存读写顺理成章地变为「自进程读写」，完全绕开了权限壁垒。

渲染方面，旧方案依赖独立 App 的 GLSurfaceView；新方案则通过 Hook eglSwapBuffers 函数，在游戏每帧交换缓冲区的时机插入 ImGui 绘制，实现菜单与 ESP 透视的无缝叠加。触摸输入则通过直接读取 /dev/input/event* 设备节点来捕获，不影响游戏本身的触摸响应。

2. 架构对比

下表从七个维度对比 独立悬浮窗模式（旧） 与 直装模式（新） 的核心差异：

对比维度 独立悬浮窗模式（旧） 直装模式（新）
运行方式 独立 App 进程，与游戏分属两个进程 注入 .so 到游戏 APK，与游戏同进程运行
内存读写 跨进程 process_vm_readv（目标 PID 为游戏进程） 同进程 process_vm_readv(getpid())，无需 root
Root 需求 需要 root 或 sharedUserId 完全不需要
用户体验 需先开修改器再开游戏，两步操作 打开游戏即自动加载，开箱即用
安装方式 修改器 App + 游戏 App 分别安装 仅需安装一个注入后的游戏 APK
渲染方式 GLSurfaceView 独立渲染上下文 Hook eglSwapBuffers，复用游戏 EGL 上下文渲染
触摸输入 Android onTouchEvent（悬浮窗内） 轮询 /dev/input/event* 原始触摸事件（只读，不消费）
关键区别总结：旧方案是「旁路」——站在游戏进程之外去窥探；新方案是「内嵌」——把自己变成游戏的一部分。这一从「外」到「内」的转变，是免root的根基。

3. 新增/修改文件清单

直装模式涉及以下文件的新增与修改：

  • app/src/main/jni/app/And64InlineHook.h 新增
    ARM64 内联 Hook 库。用于 Hook eglSwapBuffers 函数，原理是在目标函数入口写入 LDR X16 / BR X16 跳转指令并构建 trampoline 跳板，使每帧渲染时都能插入 ImGui 绘制。
  • app/src/main/jni/app/Inject.h 新增
    直装注入核心模块。包含四大功能：JNI_OnLoad 自动启动入口、eglSwapBuffers Hook 渲染循环、触摸轮询线程（/dev/input/event*）、以及从 assets 加载字体的逻辑。通过 #ifdef DIRECT_INSTALL 条件编译启用。
  • app/src/main/jni/app/Memory.h 修改
    getPID() 在 DIRECT_INSTALL 宏定义下直接返回 getpid()（而非遍历 /proc 查找游戏包名）；mem_addr_virtophy() 修复为使用 /proc/self/pagemap 读取页表，并修正了缺页检查逻辑。
  • app/src/main/jni/app/main.cpp 修改
    在文件末尾（所有函数和全局变量定义之后）引入 Inject.h，确保直装模块能正确引用 BeginDraw / DrawPlayer / EndDraw 等渲染函数和 pid / font 等全局变量。通过 #ifdef DIRECT_INSTALL 条件包含。
  • app/src/main/jni/Android.mk 修改
    添加 DIRECT_INSTALL 构建开关。当传入 DIRECT_INSTALL=true 时，追加 -DDIRECT_INSTALL 预处理宏，启用所有条件编译的直装代码路径。
  • repackage.py 新增
    APK 注入重打包脚本。使用 apktool 解包游戏 APK，将 libCube.so 注入到 lib/arm64-v8a/，将 Font.ttf 注入到 assets/，修改 smali 添加 System.loadLibrary("Cube")，最后重新打包并签名。
  • build_direct_install.bat 新增
    Windows 一键编译脚本。检查 ndk-build 是否可用，自动切换到 jni 目录执行 ndk-build DIRECT_INSTALL=true，产出 libCube.so。

4. 编译步骤

  1. 安装 Android NDK

    从 官方下载页 获取 NDK，确保 ndk-build 命令在系统 PATH 中。本项目仅支持 arm64-v8a 架构。

  2. 运行编译脚本（推荐）

    双击执行 build_direct_install.bat，或在命令行运行：

    REM Windows 命令行
build_direct_install.bat

  3. 手动编译（等效命令）

    REM 切换到 jni 目录并编译
cd app\src\main\jni
ndk-build DIRECT_INSTALL=true

  4. 确认产出文件

    编译成功后，动态库产出在以下路径：

    app/src/main/jniLibs/arm64-v8a/libCube.so   # 主输出
app/src/main/obj/local/arm64-v8a/libCube.so  # 中间产物

    编译日志中应看到：===== 直装(免root)模式编译 =====，确认 DIRECT_INSTALL 宏已生效。

提示：如果不带 DIRECT_INSTALL=true 参数直接运行 ndk-build，则编译为独立悬浮窗模式（需 root），不会包含 Inject.h 的直装注入逻辑。

5. 打包步骤

  1. 安装依赖环境

    需要以下工具已安装并加入 PATH：

    Python 3.x      # 运行 repackage.py
apktool         # APK 反编译/重编译
Java (JRE/JDK)  # apksigner / jarsigner / keytool 签名工具

  2. 运行打包脚本

    # 基本用法（自动查找 libCube.so）
python repackage.py 游戏原版.apk

# 指定 libCube.so 路径
python repackage.py 游戏原版.apk app/src/main/jniLibs/arm64-v8a/libCube.so

  3. 脚本自动执行流程

    阶段操作内容
    [1]用 apktool d 解包游戏 APK
    [2]将 libCube.so 复制到 lib/arm64-v8a/，删除其他架构目录
    [3]将 Font.ttf 复制到 assets/
    [4]修改 smali 代码，在 Application/Activity 启动时注入 System.loadLibrary("Cube")
    [5]用 apktool b 重新打包为 APK
    [6]生成调试签名密钥并签名（apksigner 或 jarsigner）

  4. 确认产出文件

    游戏原版_直装.apk   # 最终签名包，位于当前工作目录
smali 注入说明：脚本会优先在 Application 类的 onCreate / attachBaseContext 方法中注入 loadLibrary("Cube")；若无法找到，则回退到 <clinit> 静态初始化块或主 Activity。注入的 smali 代码如下： 
# ---- 直装注入: 加载修改器 .so ----
const-string v0, "Cube"
invoke-static {v0}, Ljava/lang/System;->loadLibrary(Ljava/lang/String;)V
# ---- 注入结束 ----

6. 安装与使用

  1. 卸载原版游戏

    直装 APK 使用调试签名，与官方游戏签名不同，不能覆盖安装。必须先完全卸载原版游戏（数据也会清除），再安装直装版。

  2. 安装直装 APK

    # 通过 adb 安装
adb install 游戏原版_直装.apk

# 或直接在手机上点击安装

  3. 打开游戏

    启动游戏后，修改器菜单会自动显示在屏幕上（JNI_OnLoad 在 loadLibrary 时自动执行，无需任何手动操作）。

  4. 音量键切换菜单

    按 音量下键 切换菜单的显示/隐藏状态。ESP 透视等功能在菜单隐藏时仍然正常运行（仅菜单 UI 隐藏，绘制逻辑不受影响）。

  5. 触摸操作菜单

    直接用手指点击菜单按钮即可操作。触摸事件通过 /dev/input/event* 以只读方式捕获，不会消费事件，游戏本身的触摸操作不受影响。

7. 工作原理详解

注入流程图：游戏启动 → 加载 .so → JNI_OnLoad → Hook 渲染函数 → 每帧绘制 ImGui

阶段一：启动加载

游戏启动时，由于 smali 中已被注入 System.loadLibrary("Cube")，系统会自动加载 libCube.so。加载瞬间触发 JNI_OnLoad 入口函数，整个直装注入流程由此开始：

// Inject.h — JNI_OnLoad 入口
extern "C" JNIEXPORT jint JNICALL JNI_OnLoad(JavaVM *vm, void *reserved) {
    g_vm = vm;
    pid = getpid();  // 关键: 设置为自身进程 PID
    // 启动等待线程 (Hook eglSwapBuffers)
    pthread_create(&hook_tid, nullptr, WaitAndHookThread, nullptr);
    // 启动触摸轮询线程
    pthread_create(&g_touch_tid, nullptr, TouchPollThread, nullptr);
    return JNI_VERSION_1_6;
}

阶段二：等待并安装 Hook

WaitAndHookThread 线程通过轮询 /proc/self/maps 检测 libUE4.so 是否已加载。确认加载后，使用 dlsym 获取 eglSwapBuffers 函数地址，再调用 A64HookFunction 安装内联 Hook：

// 等待 libUE4.so 加载 (最多 ~30 秒)
while (true) {
    // 读取 /proc/self/maps 查找 libUE4.so
    if (found_libUE4) break;
    usleep(100000);  // 100ms 轮询间隔
}

// Hook eglSwapBuffers
void *egl_swap = dlsym(RTLD_DEFAULT, "eglSwapBuffers");
A64HookFunction(egl_swap, hook_eglSwapBuffers, &orig_eglSwapBuffers);

阶段三：每帧渲染 ImGui

Hook 安装后，游戏每次调用 eglSwapBuffers 交换帧缓冲时，实际执行的是 hook_eglSwapBuffers。该函数在首帧初始化 ImGui（OpenGL3 + Android 后端，从 assets 加载中文字体），随后每帧执行完整的渲染流程：

static EGLBoolean hook_eglSwapBuffers(EGLDisplay dpy, EGLSurface surface) {
    // 获取当前画面尺寸
    eglQuerySurface(dpy, surface, EGL_WIDTH, &width);
    eglQuerySurface(dpy, surface, EGL_HEIGHT, &height);

    // 首帧初始化 ImGui
    if (!g_Initialized) DirectInstallInit();

    // 每帧渲染
    ImGui_ImplOpenGL3_NewFrame();
    ImGui_ImplAndroid_NewFrame(screenWidth, screenHeight);
    ImGui::NewFrame();

    if (g_menu_visible) { BeginDraw(); 颜色初始化(); }
    DrawPlayer(ImGui::GetBackgroundDrawList());  // ESP 始终绘制
    if (g_menu_visible) EndDraw();

    ImGui::Render();
    ImGui_ImplOpenGL3_RenderDrawData(ImGui::GetDrawData());

    return orig_eglSwapBuffers(dpy, surface);  // 调用原始函数
}
注意：Hook 函数中不调用 glClear，否则游戏画面会被清除。ImGui 的绘制数据叠加在游戏画面之上，最后由原始 eglSwapBuffers 统一呈现到屏幕。

阶段四：触摸输入捕获

TouchPollThread 线程负责捕获触摸事件。它扫描 /dev/input/event0 ~ event15，通过 ioctl(EVIOCGBIT) 检测支持 ABS_MT_POSITION_X 的设备（即触摸屏），然后持续读取 input_event 结构体：

// 查找触摸设备
for (int i = 0; i < 16; i++) {
    snprintf(path, "/dev/input/event%d", i);
    if (支持 ABS_MT_POSITION_X) { fd = tmp; break; }
}

// 轮询事件
while (true) {
    read(fd, &ev, sizeof(ev));
    switch (ev.type) {
        case EV_ABS:  // 原始坐标 X/Y
        case EV_KEY:  // BTN_TOUCH 按下/抬起, KEY_VOLUMEDOWN 切换菜单
        case EV_SYN:  // 转换坐标 → io.MousePos
    }
}

触摸原始坐标通过 (raw - min) / range * screen 公式转换为屏幕像素坐标，写入 ImGui::GetIO().MousePos 和 io.MouseDown[0]。由于采用 O_RDONLY 只读模式打开设备，事件不会被消费，游戏仍能正常收到触摸输入。

阶段五：内存读写（免root核心）

所有内存读写操作最终调用 process_vm_readv / process_vm_writev 系统调用。在直装模式下，getPID() 返回 getpid()（自身进程 ID），Linux 内核对自身进程的 process_vm_readv 调用不检查 root 权限：

// Memory.h — 直装模式下的 getPID()
int getPID(const char *packageName) {
#ifdef DIRECT_INSTALL
    return getpid();  // 返回自身 PID, 无需 root
#else
    // 旧模式: 遍历 /proc 查找游戏包名对应的 PID
#endif
}

// 实际内存读取 (pid = getpid())
ssize_t process_v(pid_t __pid, ...) {
    return syscall(process_vm_readv_syscall, __pid, ...);
}
这是整个免root方案的基石：旧方案中 pid 是游戏进程 ID（不同于修改器进程），跨进程读写需要 CAP_SYS_PTRACE（即 root）；新方案中 pid == getpid()，内核允许进程读写自身内存，无需任何特殊权限。

8. 注意事项与故障排查

1. 签名校验 / 反篡改检测
游戏可能内置签名校验或 APK 完整性检测机制。直装版使用了调试签名，与官方签名不同，可能触发检测导致闪退或封号。需要额外的反检测绕过方案（如 Hook 签名校验函数、修改 PackageManager 返回值等）。
2. 触摸设备路径差异
不同设备的触摸设备节点路径可能不同（/dev/input/event0 ~ event15）。如果菜单无法响应触摸，请通过 logcat 过滤 "DirectInstall" 标签查看日志： 
adb logcat -s DirectInstall
日志中会打印找到的触摸设备路径。若显示「未找到触摸设备」，说明当前设备的触摸节点不在扫描范围内，需修改 TouchPollThread 中的扫描逻辑。
3. eglSwapBuffers Hook 的指令限制
And64InlineHook 采用覆盖函数入口前 16 字节（4 条 ARM64 指令）的方式安装 Hook。这要求目标函数前 4 条指令不能包含 PC 相对寻址指令（如 B / BL / ADR / ADRP / LDR literal）。标准的 eglSwapBuffers 函数序言通常为 STP / MOV 等指令，不受此限制。若 Hook 后游戏崩溃，可能是目标函数序言不满足要求。
4. 内存偏移地址随版本变化
代码中使用的内存偏移地址（如 libbase + 0xXXX、Gname、Uworld 等全局偏移）是针对特定游戏版本硬编码的。游戏版本更新后，UE4 引擎重新编译会导致偏移地址变化，需要重新逆向定位。可通过 get_module_base(pid, "libUE4.so") 获取基址后重新计算。
5. 字体加载失败
如果菜单文字显示为方块（豆腐块 □□□），说明中文字体加载失败。请确认 Font.ttf 已被正确注入到游戏 APK 的 assets/ 目录中。可解包直装 APK 检查 assets/Font.ttf 是否存在。logcat 中搜索 "assets/Font.ttf 未找到" 可确认加载状态。
6. 安卓 11+ 分区存储限制
Android 11 及以上版本引入了 Scoped Storage（分区存储）机制，部分文件系统访问行为发生变化。虽然直装方案主要通过 /proc/self/maps、/dev/input/event*、process_vm_readv 等系统级接口工作（不受分区存储限制），但若涉及外部存储文件读写，可能需要额外适配。
